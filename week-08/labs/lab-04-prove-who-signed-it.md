## Mission

Create a separate signing key pair, sign the incident report, verify the original, then prove that the same signature fails against a changed copy.

## What You Already Know

A digital signature uses a private key to sign and the matching public key to verify. Verification supports integrity and authenticity claims about the key. It does not encrypt the report or prove which human physically used the private key.

## Predict First

**[WORKSHEET]** Should the original signature verify after the report content changes? Explain.

```text
No, the original signature will not verify after the report content changes.
A digital signature is generated by hashing the original file content and encrypting that hash with the signer's private key. If the report content is modified in any way, recalculating its hash will produce a completely different value, causing the verification process to fail because the newly calculated hash no longer matches the decrypted original signature.
```

## Explain

**[WORKSHEET]** In 4–5 sentences, explain both verification results and why signing is not encryption.

```text
The original report returned Verified OK because its cryptographic hash matched the hash recovered from the signature file using the public key, confirming the file remained untouched. When I modified the report, its cryptographic hash changed completely, causing the verification process to output Verification failure against the original signature. Digital signing provides data integrity and authenticity by proving who signed the document and that it hasn't been altered. However, it does not provide confidentiality like encryption does, which is why I could still open and read the underlying report content in plain text.
```

## Analysis Questions

1. What does `Verified OK` establish within this lab?

```text
In this lab, Verified OK establishes two key security properties:
Integrity: It proves that the evidence/incident-report.txt file has not been altered or tampered with since I signed it.
Authenticity: It proves that the signature was generated using the private key that pairs directly with my public key (week8_signing_public.pem)
```

2. Why did the changed copy fail verification?

```text
The changed copy failed verification because modifying the file altered its contents, causing OpenSSL to compute a completely different SHA-256 hash during verification. When OpenSSL decrypted the original signature using my public key, the recovered hash did not match the newly calculated hash of the modified file, resulting in a Verification failure.
```

3. Why is the signed report still readable?

```text
The signed report is still readable because creating a digital signature does not encrypt or scramble the contents of the file. The signing process generates a separate cryptographic signature file (incident-report.sig) based on the report's hash, leaving the original text file (incident-report.txt) in plain text and readable by anyone.
```

4. Why does the signature alone not prove which human used the private key?

```text
The signature alone only proves possession and use of the specific private key, not the identity of the physical person operating the system. A private key can be shared, stolen, copied, or accessed by unauthorized individuals or automated processes. Without secondary authentication measures like multi-factor authentication, biometric verification, or a trusted identity framework, I cannot prove that a specific human physically initiated the signing operation.
```
